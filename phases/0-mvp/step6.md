## 작업

### 1. 진입 — `src/app/(student)/s/[code]/page.tsx`

`[code]`는 **특강 회차의 입장 코드 6자리**다 (학생 가명코드가 아니다).

Server Component에서 `lecture_sessions`를 입장 코드로 조회한다.

- 없는 코드 → "코드를 다시 확인해주세요" 안내. 404 페이지를 그대로 노출하지 마라.
- 회차가 닫혀 있으면 닫힘 안내.
- 유효하면 학생 진입 화면을 띄운다.

### 2. 학생 식별 화면

```
[ 참여 코드 입력 ]      ← 기관이 배부한 학생 가명코드
      또는
 코드 없이 참여하기      ← 익명 응답
```

코드가 `students`에 없으면 "코드를 확인해주세요"로 되돌리되, **익명 진입 경로를 항상 함께 보여준다.** 코드 문제로 학생을 돌려보내면 응답 자체를 잃는다.

### 3. 문항 화면 (Client Component)

`/docs/SURVEY.md`의 Q1~Q7을 구현한다.

- **한 화면에 한 문항.** 진행률을 항상 표시한다.
- Q1~Q4 필수, Q5~Q7 선택.
- **조건부 분기: Q3이 3 또는 4일 때만 Q5·Q6·Q7을 보여준다.** 1 또는 2면 Q4에서 바로 제출로 간다.
- Q4의 "아직 잘 모르겠어요"는 단독 선택이다 — 고르면 다른 선택이 해제되고, 다른 것을 고르면 이게 해제된다.
- 뒤로 가기로 앞 문항을 수정할 수 있어야 한다.
- 애니메이션은 UI_GUIDE가 허용한 `slide-up`(0.25s)만. `prefers-reduced-motion`에서는 끈다.

### 4. 제출 API — `src/app/api/survey/route.ts`

```ts
// 요청 본문 타입
type SurveySubmission = {
  sessionCode: string
  pseudoCode: string | null       // null이면 익명
  grade: string
  satisfaction: 1 | 2 | 3 | 4 | 5
  followupIntent: 1 | 2 | 3 | 4
  interestFields: string[]        // 최대 3개
  wantToLearn?: string            // 최대 200자
  desiredJob?: string             // 최대 50자
  availableTimes?: string[]
}
```

서버에서 반드시 할 일:

1. 스키마 검증 — 범위 밖 값, 4개 이상의 분야, 길이 초과는 거부한다. 클라이언트 검증을 신뢰하지 마라.
2. **자유 서술 2개를 `maskSensitive()`로 마스킹한 뒤 저장한다.** 마스킹 전 원문을 저장하거나 로그에 남기지 마라.
3. `interestFields`가 `/docs/SURVEY.md`의 5개 분야 + "모르겠음" 집합에 속하는지 확인한다.
4. 중복 제출 — `(session_id, student_id)` 유니크 위반은 에러 화면이 아니라 "이미 응답했어요" 안내로 처리한다.
5. 성공 시 추천 결과 경로로 보낼 식별자를 응답에 담는다.

익명 응답은 서버에서 중복을 막을 수 없다. 브라우저 저장소로 약하게만 막고, **서버에서는 막지 마라** — 같은 교실에서 같은 기기를 돌려 쓰는 경우가 있다. (E-04)

마감된 회차(`status = 'closed'` 또는 `closes_at` 경과)의 제출은 거부하고 E-01과 같은 안내로 처리한다. (E-17)

### 4-1. 제출 실패 복구 (E-05 — 반드시 구현)

교실 와이파이는 불안정하다. **제출이 실패하면 학생의 답이 사라지는 구조를 만들지 마라.**

- 각 문항 응답을 입력 즉시 브라우저 저장소에 임시 보관한다.
- 제출 실패 시 에러 화면이 아니라 **재시도 버튼**을 보여준다.
- 새로고침·뒤로가기·앱 전환 후 돌아와도 입력값이 남아 있어야 한다.
- 제출 성공 시 임시 보관값을 지운다.

### 5. 제출 후

제출 즉시 추천 결과 경로로 이동한다. **"제출 완료" 중간 화면을 만들지 마라.** 관심이 가장 뜨거운 순간을 한 번 더 끊는다.

이 step에서는 추천 결과 페이지를 플레이스홀더로 둔다(step 7·8에서 채운다).

### 6. 테스트 (TDD — 먼저 작성)

1. 없는 회차 코드 → 안내 화면(에러 페이지 아님)
2. Q3이 2일 때 Q5·Q6·Q7을 건너뛴다
3. Q3이 3일 때 Q5·Q6·Q7이 노출된다
4. Q4에서 4개 선택 시도 → 거부
5. Q4 "모르겠음"과 다른 항목의 상호 배타
6. 자유 서술에 전화번호를 넣으면 저장된 값이 마스킹돼 있다
7. `satisfaction: 6` 같은 범위 밖 값 → 서버가 거부
8. 같은 가명코드로 같은 회차 2회 제출 → 안내 응답(500 아님)
9. 익명 제출이 정상 저장된다
10. 필수 문항 미응답 → 다음으로 진행 불가
11. 마감된 회차 제출 → 거부 + 안내 (E-17)
12. **제출 실패 후 재시도로 성공한다. 새로고침해도 입력값이 유지된다 (E-05)**

1. 위 AC 커맨드를 실행한다.
2. 아키텍처 체크리스트를 확인한다:
   - SURVEY.md의 문항과 1:1로 일치하는가? (문항 수, 필수·선택, 분기 조건, 라벨)
   - 자유 서술이 마스킹 후 저장되는가?
   - UI_GUIDE 학생 화면 규칙(48px 터치 타깃, 16px 이상 폰트, 한 화면 한 문항)을 지키는가?
   - 개인정보 입력란이 없는가?
   - CLAUDE.md CRITICAL 규칙을 위반하지 않았는가?
3. 결과에 따라 `phases/0-mvp/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- 이름·연락처·학교·생년월일 입력란을 만들지 마라. 이유: 플랫폼이 학생 PII를 보유하지 않는다는 전제로 법적 구조 전체가 설계됐다(ADR-003).
- 만족도와 후속 의향을 한 문항으로 합치지 마라. 이유: 후속 의향이 파일럿의 1차 전환 지표다. 합치면 "재미있었다"와 "더 배우고 싶다"를 구분할 수 없다.
- 문항을 추가하지 마라. 이유: 3분을 넘기면 뒤쪽 문항의 응답 품질이 무너진다.
- 공급이 없는 분야(VR·AR, AI·코딩, 뷰티)를 선택지에서 빼지 마라. 이유: 미충족 수요가 제품의 핵심 데이터다. 빼면 수요가 있다는 사실 자체를 알 수 없다.
- 익명 응답을 서버에서 차단하지 마라. 이유: 같은 교실에서 기기를 공유하는 경우가 있고, 응답률이 이력보다 중요하다.
- 추천 로직을 여기서 만들지 마라. 이유: step 7의 작업이다.
- 기존 테스트를 깨뜨리지 마라.
