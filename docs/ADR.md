# Architecture Decision Records

## 철학

1. **안전 설계는 타협 대상이 아니다.** 미성년자 대상 서비스이므로, 속도를 위해 안전 제약을 미루는 선택은 하지 않는다. 나머지는 전부 타협 가능하다.
2. **MVP 속도 최우선.** 1차 검증 가설은 "특강 들은 학생이 실제로 후속 교육까지 넘어가는가" 하나다. 수요 주체를 3종(학교·기관·개인)으로 넓혔지만 **화면 수를 넓히지 않는다** — 개인 경로는 공개 디렉토리와 문의 폼 2화면이 전부다. 이 가설들과 무관한 기능은 만들지 않는다.
3. **외부 의존성 최소화.** 지도 API, 결제 PG, 문자 발송 등은 MVP에서 전부 배제한다.
4. **작동하는 최소 구현을 선택한다.** 강사 심사·모더레이션은 자동화하지 않고 사람이 한다.
5. **AI는 제품이 아니라 공급자의 도구다.** 학생에게 가는 AI는 QR을 찍을 이유 한 줄까지다. 그 이상의 AI 투자는 전부 강사·기관 쪽으로 간다. 이유는 두 개다 — 돈을 내는 쪽의 노동을 줄여야 구독이 성립하고, 학생 데이터를 늘리지 않아야 ADR-003이 유지된다.

---

### ADR-001: Next.js 15 App Router + TypeScript strict
**결정**: Next.js 15 App Router, TypeScript strict mode, Tailwind CSS.
**이유**: 학생용 모바일 웹과 기관용 대시보드를 한 코드베이스에서 처리해야 한다. Server Components로 대시보드 조회 코드를 얇게 유지할 수 있다.
**트레이드오프**: 앱(네이티브)을 포기한다. 학생이 특강 현장에서 QR로 진입하는 시나리오라 앱 설치 요구는 전환율을 죽인다. 웹이 맞다.

### ADR-002: Supabase + RLS로 권한 분리
**결정**: Supabase(Postgres + Auth + Storage)를 쓰고, 5종 주체(학생·보호자·강사·기관/학교 담당자·운영자)의 권한 분리를 **RLS 정책으로 DB 레벨에서 강제**한다. 학생과 보호자는 계정이 없으므로 둘 다 anon 역할로 들어오지만 **열 수 있는 문이 다르다** — 학생은 설문 INSERT, 보호자는 `inquiries` INSERT다.
**이유**: 이 서비스에서 가장 치명적인 사고는 "학생 화면에 강사 연락처가 노출" 또는 "타 기관 학생 데이터 조회"다. 애플리케이션 코드 체크는 새 화면을 추가할 때마다 빠뜨릴 수 있다. RLS는 쿼리를 어디서 날리든 적용된다. 강사 증빙 파일도 Storage 비공개 버킷으로 한 번에 해결된다.
**트레이드오프**: RLS 정책 작성·테스트 비용이 추가된다. 네거티브 테스트(권한 없는 역할이 접근하면 실패)를 반드시 써야 하므로 초기 속도가 약간 느려진다. 이 비용은 지불한다.

### ADR-003: 학생은 기관 발급 가명코드로만 식별
**결정**: 학생 실명·연락처·학교명을 저장하지 않는다. `students` 테이블은 가명코드·기관ID·학년까지만 가진다. 코드↔실명 매핑은 기관이 보유한다.
**이유**: 만 14세 미만 법정대리인 동의(개인정보보호법) 부담을 구조적으로 회피하면서 관심 이력은 누적할 수 있다. 플랫폼은 기관의 개인정보 처리 수탁자 지위가 된다.
**트레이드오프**: 학생 본인에게 직접 알림(문자·메일)을 보낼 수 없다. 모든 통지는 기관을 경유한다. 코드를 분실한 학생은 이력이 끊긴다 — 익명 응답 허용으로 완화한다.

### ADR-004: AI 추천은 규칙 필터 + LLM 하이브리드
**적용 범위**: 이 ADR은 **학생이 보는 추천 카드**에만 적용된다. 강사가 보는 수업 설계 도우미는 ADR-017이며, 하이브리드 구조와 폴백 원칙을 그대로 따른다.
**결정**: 2단 구조로 만든다.
1. **규칙 필터** — 지역(시군구→인접→시도), 대상 학년, 관심 분야, 승인 상태로 후보를 추린다. 순수 SQL.
2. **LLM** — 추려진 후보 중 순위를 정하고 **추천 이유 한 줄**을 한국어로 생성한다. 모델은 `claude-opus-5` (입력 $5 / 출력 $25 per MTok), `thinking: {type: "adaptive"}`, `output_config.effort: "low"`, 응답은 structured outputs(`output_config.format`)로 JSON 스키마를 강제한다.

**이유**: 전부 LLM에 맡기면 존재하지 않는 강사를 추천하는 환각이 발생하고, 전부 규칙으로 하면 "왜 이걸 추천했는지"를 학생 언어로 설명할 수 없다. 추천 이유 한 줄이 학생의 전환을 만드는 실제 장치이므로 이 부분만 LLM에 맡긴다. 후보가 SQL로 이미 확정되므로 환각 가능성이 구조적으로 차단된다.

**핵심 규칙 (반드시 지킬 것)**:
- **LLM 호출이 실패하면 규칙 기반 순위만으로 화면을 렌더한다.** AI가 죽어도 추천 화면은 떠야 한다. LLM 응답을 화면의 필수 조건으로 만들지 말 것.
- **학생 자유 텍스트를 LLM에 보내기 전 연락처·이름 패턴 마스킹 필터를 통과시킨다.** 학생이 설문 자유 서술란에 본인 실명이나 연락처를 적을 수 있다. `lib/moderation`의 필터를 재사용한다.
- LLM 호출은 `app/api/recommend/`에서만. API 키가 클라이언트로 가는 경로를 만들지 말 것.

**비용 추정**: 요청당 입력 약 2K · 출력 약 500 토큰 가정 시 건당 약 $0.02(30원 내외). 파일럿 규모(수백 건)에서는 무의미한 수준이다.

**트레이드오프**: 추천 생성에 1~3초 지연이 붙는다. 설문 제출 직후 화면이므로 로딩 상태를 성의 있게 만들어야 한다. 비용이 문제가 되면 `claude-sonnet-5`(입력 $2 / 출력 $10)로 내리는 선택지가 있으나, 품질 확인 전에 먼저 내리지는 않는다.

### ADR-005: 지역 인접 관계는 JSON 하드코딩, 범위는 수도권 66개, 확장은 2-hop
**결정**: 행정구역 코드와 인접 시군구 관계를 `src/data/region-adjacency.json`에 정적으로 둔다. 지도 API·지오코딩을 쓰지 않는다. 범위는 **수도권 66개 시군구**(서울 25 + 경기 31 + 인천 10)로 시작하고 전국 229개를 한 번에 만들지 않는다. 확장 단계는 `같은 시군구 → 인접(1-hop) → 인접의 인접(2-hop)`이며 **"같은 시도" 단계를 쓰지 않는다.**
**이유**: 필요한 연산은 "이 시군구에 붙어 있는 시군구 목록"뿐이다. 외부 API 키·요금·장애 지점을 하나 줄인다. 시도 단계를 버리는 이유는 파일럿 지역 때문이다 — 광명시의 인접 5곳(서울 구로구·금천구, 경기 시흥시·부천시·안양시) 중 2곳이 서울이다. 경계 도시에서 "같은 시도"는 거리와 무관한 기준이 된다. 수도권으로 범위를 한정하면 광명시 파일럿에 필요한 전부를 덮으면서 데이터 작업이 1/3로 줄고, 2-hop 확장이 서울·경기·인천을 자연스럽게 넘나든다.
**트레이드오프**: 직선거리 기반 정밀 추천이 불가능하다. 수도권 밖으로 확장할 때 데이터를 추가해야 한다. 행정구역이 개편되면 수동 갱신해야 한다. 셋 다 MVP에서 문제되지 않는다.

### ADR-006: 1:1 메시지를 만들지 않는다 (영구 결정)
**결정**: 학생↔강사 소통은 기관 담당자가 열람 가능한 공개 Q&A 스레드만 제공한다. DM 테이블·API·UI를 만들지 않는다.
**이유**: 비공개 채널이 하나라도 생기면 "안전한 관리 체계 안의 연결"이라는 제품의 전제가 무너지고, 학교·기관 도입 논리도 같이 무너진다. 연락처·외부 링크 자동 차단은 안전 목적이자 플랫폼 외부 이탈 방지 목적을 겸한다.
**트레이드오프**: 학생의 개별 상담 수요를 받을 수 없다. 기관 담당자를 경유하게 한다. 이 불편은 의도된 것이다. 개인 단위 수요는 **성인 보호자의 문의 폼**으로만 받는다(ADR-014) — 주체가 성인이라는 점이 이 예외를 허용하는 유일한 근거다.

### ADR-007: MVP에 결제를 넣지 않는다
**결정**: 기관·학교 경로의 후속 교육 비용은 기관 사업비로 집행된다. 개인(보호자) 경로의 수강료도 플랫폼 밖에서 강사와 직접 정산된다. PG 연동·정산·환불·수수료를 만들지 않는다.
**이유**: 결제가 들어오면 환불 정책, 사고 책임, 정산 주기, 세금계산서가 전부 따라온다. 검증할 가설과 무관하다.
**트레이드오프**: 중개 수수료 수익을 Phase 2로 미룬다. MVP 수익은 구독 2종(강사·업체 / 학교·기관)만 가정한다. 개인 경로에서는 문의가 실제 수업으로 성사됐는지를 플랫폼이 알 수 없으므로 운영자가 수동 추적한다(ADR-014).

### ADR-008: 강사 심사와 모더레이션은 사람이 한다
**결정**: 강사 자격·성범죄경력 조회 증빙은 운영자가 수동 확인한다. Q&A 신고 처리는 기관 담당자가 한다. 자동 심사 API를 붙이지 않는다.
**이유**: 초기 강사는 20~30명 규모이고 기존 네트워크 기반이다. 자동화할 물량이 아니다. 판단 실수의 비용이 크므로 사람이 보는 게 맞다.
**트레이드오프**: 강사 수가 수백 명을 넘으면 병목이 된다. 그때 다시 결정한다.

### ADR-009: 추천 순위에 소속 업체와 구독 여부를 반영하지 않는다
**결정**: 추천·검색·**공개 디렉토리 정렬** 로직의 입력은 지역 근접도, 분야 일치도, 대상 학년 적합성, 학생의 누적 관심 이력뿐이다. 강사의 소속 업체·구독 등급·결제 여부를 순위에 넣지 않는다. 유료 노출 슬롯도 만들지 않는다.
**이유**: 첫 강사 공급이 3DNFLY 한 곳에서 나온다. 이 상태에서 순위가 소속이나 과금에 반응하면 플랫폼은 특정 업체의 영업 도구가 되고, 2호 업체가 들어올 이유가 사라진다. 기관이 "이건 특정 업체 홍보"로 판단하면 수요 데이터 자체를 신뢰하지 않는다. 중립성은 나중에 추가할 수 없다 — 처음부터 로직에 없어야 증명할 수 있다.
**트레이드오프**: 구독의 가치 제안이 "노출 우대"가 아니라 "지역 수요 알림 + 섭외 리드 + 보호자 문의 리드 + 학교 제출용 회차 리포트 + Q&A를 통한 전문성 노출"로 제한된다. 더 어려운 판매지만 플랫폼의 신뢰를 파는 쪽이 맞다.

### ADR-010: 공급자는 업체 ↔ 강사 2계층으로 모델링한다
**결정**: `providers`(교육업체)와 `instructors`(강사)를 분리하고 `instructors.provider_id`를 nullable로 둔다. 프리랜서 강사는 소속 없이 존재할 수 있다.
**이유**: 국내 진로교육 공급의 실제 형태는 개인 강사가 아니라 업체의 출강이다. 첫 파트너 3DNFLY도 업체이고 강사가 여러 명 소속돼 있다. 구독 과금 주체와 섭외 요청 수신 주체가 업체인 경우가 많으므로, 업체를 1급 개체로 두지 않으면 나중에 전부 고쳐야 한다.
**트레이드오프**: MVP에 테이블과 화면이 하나 늘어난다. 현재 업체가 1곳이라 과잉 설계로 보이지만, 2호 업체를 받는 시점의 마이그레이션 비용보다 싸다.

### ADR-011: 모든 계정은 초대 기반. 셀프 가입을 만들지 않는다
**결정**: 기관 담당자·강사·운영자 계정은 운영자가 보낸 초대 링크로만 생성된다. 공개 회원가입 화면을 만들지 않는다. 로그인은 이메일 매직링크이며 비밀번호를 저장하지 않는다. 초대 토큰은 1회용이고 만료시각을 가진다.
**이유**: 셀프 가입을 열면 아무나 "○○중학교 진로전담교사"를 자칭해 계정을 만들고, 그 기관으로 배정받아 학생 데이터를 열 수 있다. RLS로 기관 간 격리를 해도 **가입 단계에서 소속을 검증하지 않으면 무의미하다.** 미성년자 데이터를 다루는 서비스에서 이 구멍은 감당할 수 없다. 파일럿 기관이 1곳이라 초대 운영 부담도 사실상 없다.
**트레이드오프**: 강사가 스스로 찾아와 등록하는 유입 경로가 막힌다. 플랫폼 성장 속도를 일부 포기한다. 강사 셀프 등록은 신원 검증 체계를 갖춘 뒤에 연다.
**개정 (2026-09-19, 사용자 결정 — 첫 교실 파일럿)**: 로그인을 **아이디·비밀번호**로 바꾼다. 교실 공용 PC 에서 강사가 메일함을 열지 않고 바로 로그인해 QR 을 띄워야 하기 때문이다. 영문·숫자 아이디는 메일이 배달되지 않는 예약 도메인(`@findmymento.invalid`) 주소로 Supabase 이메일+비밀번호 로그인에 얹는다(`lib/auth/login-id.ts`). 로그인 직후 역할은 새 요청(`/login/after`)에서 세 테이블 조회로만 판별하고, 오늘 배정된 회차가 있는 강사는 곧장 전체화면 QR 로 간다. **셀프 가입 금지는 그대로다** — 계정은 운영자가 만들거나 초대로만 생기고, `signUp` 은 여전히 쓰지 않는다(`tests/safety-invariants.test.ts`). 비밀번호를 저장하게 된 만큼 비밀번호 재설정·변경 화면이 필요하다(후속).

### ADR-012: 배포는 Vercel, 마지막 step에서
**결정**: Vercel + Supabase 호스티드로 배포하고, 배포 작업은 마지막 step에 둔다. 단 step 0에서 Vercel 호환 설정과 환경변수 구조(`.env.example`, 서버 전용 키 분리)를 미리 잡는다.
**이유**: 사용자 결정. 개발 중 배포에 신경 쓰지 않는 쪽을 택했다.
**트레이드오프**: **QR 실물 스캔 검증이 배포 step 이후로 밀린다.** 그때까지 학생 유입 경로는 로컬 URL로만 테스트되며, 실제 휴대폰에서의 QR 동작·모바일 레이아웃 확인이 마지막에 몰린다. step 0에서 환경변수 구조를 미리 잡는 것은 이 리스크를 줄이기 위한 최소 장치다.

### ADR-013: 학교와 기관을 같은 주체로 모델링한다 (`organizations.type`)
**결정**: 학교·청소년기관·교육업체·지자체를 `organizations` 한 테이블에 `type`(`school` / `youth_center` / `edu_company` / `local_gov`)으로 담는다. 권한 로직과 RLS 정책을 type으로 분기하지 않는다. type은 화면 문구와 수요 집계 분류에만 쓴다.
**이유**: 제품의 정의가 "지역 강사를 **학교·기관·개인**과 연결한다"이므로 학교를 데이터 모델에서 빼면 정의와 구현이 어긋난다. 동시에 학교와 청소년기관이 플랫폼에서 하는 일은 완전히 동일하다 — 회차를 만들고, 강사를 배정하고, 리포트를 보고, 섭외 요청을 보낸다. 두 테이블로 쪼개면 모든 RLS 정책과 모든 쿼리가 두 벌이 되고, 그 순간 권한 누락 사고의 확률이 두 배가 된다. 학교를 Phase 2로 미루는 기존 결정은 **영업 순서의 문제였을 뿐 데이터 모델의 문제가 아니었다.**
**트레이드오프**: 학교 고유의 제약(학기 주기, 공문, 행정망, 예산 품의)이 스키마에 반영되지 않는다. MVP에서는 전부 플랫폼 밖에서 처리하므로 문제되지 않는다. 학교 전용 필드가 실제로 필요해지면 `organizations`에 nullable 컬럼을 더하거나 `school_profiles` 확장 테이블을 붙인다 — 주체를 쪼개는 것보다 싸다.

### ADR-014: 개인 수요는 공개 디렉토리 + 보호자 문의로만 받는다
**결정**: 개인(비기관) 수요 경로를 연다. 구성은 **(a) 로그인 없이 열람하는 공개 강사·프로그램 디렉토리, (b) 성인 보호자가 작성하는 비로그인 문의 폼** 둘뿐이다. 보호자 계정·로그인·마이페이지를 만들지 않는다. `inquiries` 테이블은 보호자 본인의 이름·연락처와 **학년대(초/중/고)**까지만 받고, 학생 이름·학교·생년월일 컬럼을 갖지 않는다. anon 역할은 `inquiries`에 **INSERT만** 가능하고 SELECT는 불가능하다.
**이유**: "개인과 매칭한다"를 구현하는 방법은 여러 가지지만, 미성년자 대상 서비스에서 안전하게 구현하는 방법은 하나다 — **주체를 성인으로 올리는 것.** 학생 본인이 신청하는 경로를 만들면 (1) 학생 PII가 필요해지고, (2) 법정대리인 동의 의무가 플랫폼으로 넘어오고, (3) 학생↔강사 직접 연결이 생겨 ADR-006의 전제가 무너진다. 보호자를 주체로 두면 세 문제가 동시에 사라진다. 보호자는 성인이므로 본인 정보를 본인 동의로 제공할 수 있고, 학생에 대해서는 "중학생"이라는 학년대만 남는다.
디렉토리를 **공개**로 두는 이유는 보호자가 계정을 만들 이유가 없기 때문이다. 가입 벽을 세우면 개인 경로의 유입이 0이 된다. 공개해도 안전한 것은 디렉토리에 연락처가 없기 때문이다(CRITICAL 규칙 2).
**트레이드오프**:
- 문의가 성사로 이어졌는지 플랫폼이 알 수 없다. 수강료 정산을 붙이지 않기로 했으므로(ADR-007) 성사 여부는 운영자가 수동으로 추적한다.
- anon INSERT가 열려 있으므로 스팸·도배에 노출된다. `/api/inquiry`에서 서버 검증(필수값, 길이, 금칙어, 레이트 리밋)을 거치게 하고, 폼을 Server Action/API 경유 없이 직접 INSERT하도록 만들지 않는다.
- **개인 경로를 여는 순간 플랫폼은 보호자 개인정보의 처리자가 된다.** 기관 데이터에 대한 수탁자 지위와 별개의 책임이며, 문의 폼에 수집·이용 동의문이 반드시 있어야 한다. 이건 코드가 아니라 문서 작업이다.

### ADR-015: 회차는 기관·학교만 만든다. 강사는 배정받고, 현장에서 안내한다
**결정**: `lecture_sessions`의 생성 권한은 `org_members`에게만 준다. 강사는 회차를 만들 수 없다. 대신 기관이 회차에 **배정 강사**를 지정하고(`lecture_sessions.instructor_id`, nullable), 배정된 강사는 그 회차의 **QR 투사 화면과 리포트**를 열람할 수 있다.
**이유**: 현장 사실관계가 이렇다 — 특강을 발주하고 학생을 모으고 공간을 제공하는 주체는 기관·학교이고, 강사는 출강한다. 회차 생성권을 강사에게 주면 기관 동의 없이 그 기관 학생에게 설문을 돌릴 수 있게 되고, 학생 데이터의 관리 주체(수탁 관계의 위탁자)가 누구인지 불분명해진다. 개인정보 처리위탁 계약이 기관과 체결되므로, 회차의 소유자는 반드시 기관이어야 한다.
그러나 **학생 유입의 실제 트리거는 강사의 한마디다.** 교실 벽의 QR 포스터는 아무도 찍지 않는다. 수업 마지막 3분에 강사가 "이거 찍으면 너한테 맞는 다음 교육을 AI가 찾아줘"라고 말할 때 학생이 찍는다. 그래서 강사에게는 **회차 생성 권한이 아니라 현장에서 QR을 띄울 화면과, 수업 후 학교에 제출할 리포트**가 필요하다. 이 리포트가 강사 구독료의 가장 구체적인 가치다.
**트레이드오프**:
- 기관 계정이 없는 학교에 강사가 혼자 출강하는 경우 회차를 만들 수 없다. 이때는 운영자가 대신 기관을 등록하고 회차를 만들어준다 (강사 셀프 등록을 막은 ADR-011과 같은 운영 부담).
- `instructor_id`가 nullable이므로 배정되지 않은 회차는 강사가 리포트를 못 본다. 기관이 배정을 빼먹으면 강사의 구독 가치가 사라지므로, 회차 생성 화면에서 배정을 강하게 유도해야 한다.
- 학생 유입이 강사의 구두 안내에 의존한다. 기능으로 해결할 수 없는 운영 리스크이므로 **강사용 안내 스크립트**를 파일럿 준비물에 넣는다.

### ADR-016: 학급 특성은 회차 단위 속성으로만 저장한다
**결정**: 수업 조건(시수·장소·학급 특성·보유 장비)을 `lecture_sessions`의 컬럼으로 둔다. 학생 개인 레코드(`students`, `survey_responses`)에는 어떤 경우에도 붙이지 않는다. 학급 특성 `class_traits`는 자유 텍스트가 아니라 **고정 체크박스 목록**이며 목록 밖의 값은 저장하지 않는다. 입력 주체는 회차를 만드는 기관·학교이고(ADR-015), 배정 강사는 읽기만 한다.

초기 허용 목록: `통합학급 포함` / `휠체어 사용 학생 있음` / `청각 보조 필요` / `시각 보조 필요` / `한국어 보조 필요` / `첫 경험 다수` / `경험자 다수` / `집중 지속이 짧은 편`

**이유**: 강사가 수업 전에 실제로 알아야 하는 것은 "누가 어떤 장애가 있는가"가 아니라 **"이 반에 어떤 대응이 필요한가"**다. 후자는 학생을 식별하지 않고도 전달된다. 장애·건강 정보는 개인정보보호법상 민감정보이고, 학생 개인에 귀속시키는 순간 이 서비스가 구조적으로 회피해 온 법정대리인 동의·민감정보 별도 동의 의무가 통째로 돌아온다. 회차는 "한 반의 한 수업"이라는 단위이므로 여기 붙은 특성은 개인을 지목하지 않는다.

자유 텍스트를 막는 이유는 더 실무적이다. 입력란을 열어 두면 담당 선생님이 "3번 자리 OO이 자폐스펙트럼"이라고 적는다. 악의가 아니라 친절 때문에 적는다. **선택지를 닫는 것이 유일하게 작동하는 방어다.**

**트레이드오프**: 체크박스로 표현되지 않는 현장 사정은 전달되지 않는다. 의도한 손실이다. 꼭 전달해야 하면 담당자가 강사에게 플랫폼 밖에서 말하면 된다 — 그 대화를 우리가 보관하지 않는 것이 요점이다. 목록이 부족하면 항목을 늘리되, 확장은 **항상 고정 목록에 항목을 더하는 방식**이어야 한다.

### ADR-017: 수업 설계 도우미도 규칙 + LLM 하이브리드. AI의 수혜자는 강사다
**결정**: 배정 강사가 회차 상세 화면에서 버튼 하나로 **교안 초안**을 생성한다. 구조는 ADR-004와 동일한 2단이다.
1. **규칙** — 프롬프트 입력을 결정론적으로 조립한다. 회차 조건(ADR-016) + 강사가 이미 등록한 프로그램의 `outline` + 과거 회차 설문 집계(ADR-018).
2. **LLM** — 차시 흐름(도입·전개·마무리)과 **단계별 난이도 분기**를 생성한다. 각 단계마다 `기본 / 빨리 끝낸 학생 / 어려워하는 학생`을 쓰고, 그 회차에 해당 `class_traits`가 있을 때만 대응 줄을 덧붙인다.

**LLM 호출이 실패하면 프로그램 `outline` 기반 규칙 템플릿으로 골격을 반환한다.** 화면에 에러를 띄우지 않는다 (ADR-004와 같은 원칙).

산출물 범위는 **차시 흐름 + 난이도 조절안까지**다. 학생용 활동지와 학교 제출용 계획서 서식은 MVP에서 만들지 않는다.

**이유**: 지금까지 AI는 학생 화면 한 곳에만 있었다 — 설문 직후 추천 카드. 그런데 **학생은 돈을 내지 않는다.** 구독료를 내는 것은 강사와 기관이고, 그들의 시간은 수업 준비에 들어간다. 진로체험 강사는 같은 커리큘럼을 학교마다 다시 손본다. 25명 반과 8명 반이 다르고, 통합학급이 있는 반이 다르고, 드론이 10대인 학교와 3대인 학교가 다르다. 이 조정은 매번 수작업이며, 강사가 가장 자주 포기하는 부분이 **진도 편차 대응**이다.

1차 구상에서는 AI가 학생 한 명을 개인화하려 했다. 그러려면 학생 활동 데이터가 쌓여야 하는데 첫 수업 첫 학생에게는 데이터가 0이고, 데이터를 모으려면 미성년자 개인 기록을 축적해야 한다. **개인화의 단위를 학생 한 명에서 학급 한 반으로 올리면 두 문제가 동시에 사라진다.** 학급 조건은 기관이 이미 알고 있어 첫 회차부터 입력 가능하고, 학생 개인을 식별하지 않는다.

**트레이드오프**:
- 생성 품질의 책임이 플랫폼에 붙는다. 화면에 **초안**임을 명시하고 최종 책임이 강사에게 있음을 고지한다. 검토 없이 그대로 쓰도록 유도하는 문구를 쓰지 않는다.
- 학생 화면의 AI는 지금 수준(추천 카드 + 이유 한 줄)에서 더 나아가지 않는다. 학생별 학습 수준 진단은 만들지 않는다 — 만드는 순간 ADR-003이 무너진다.
- 추천보다 출력이 길어 호출당 비용이 오른다. 건당 수백 원 수준이고 회차당 1~2회이므로 파일럿 규모에서는 무시할 수 있다.

### ADR-018: 과거 회차 설문을 교안 입력으로 쓴다. 단 응답 5건 미만이면 쓰지 않는다
**결정**: 교안을 생성할 때 **같은 기관 + 같은 분야의 지난 회차 설문 집계**를 프롬프트에 넣는다. 넣는 것은 집계값과 마스킹을 통과한 자유서술뿐이다 — 만족도 평균, 후속 의향 분포, 관심 분야 분포, `want_to_learn`에서 반복된 표현. **개별 응답을 행 단위로 넘기지 않는다.**

**해당 집계의 응답 수가 5건 미만이면 집계를 만들지 않고 프롬프트에서 통째로 뺀다.**

**이유**: "그냥 ChatGPT에 물어보면 되지 않나"에 대한 답이 이것 하나뿐이다. 범용 모델은 이 학교 학생들이 지난번 드론 특강에서 조종보다 조립에 반응했다는 사실을 모른다. 우리는 그 데이터를 이미 갖고 있다 — 학생이 특강 직후 찍은 QR에서 나왔다. 설문 → 교안 → 수업 → 다시 설문으로 닫히는 루프이며, 회차가 쌓일수록 교안이 좋아지는 유일한 구조다. **데이터가 제품을 개선하는 경로가 여기서 처음 생긴다.**

5건 임계치는 k-익명성 최소 조치다. 응답이 2건인 회차에서 "관심 분야 분포 50% 코딩"은 분포가 아니라 특정 학생 한 명의 답이다. 담당 선생님은 누가 응답했는지 대체로 알고 있으므로 작은 표본의 집계는 사실상 개인 정보가 된다. 가명코드 설계로 막아 둔 것을 집계가 우회하게 두지 않는다.

**트레이드오프**: 첫 회차에는 이 입력이 없다. 교안은 회차 조건과 프로그램 outline만으로 생성되며 품질이 낮다. 의도한 순서다 — 데이터가 쌓이기 전에 좋은 교안이 나온다면 애초에 우리 데이터가 필요 없다는 뜻이 된다. 화면에 `지난 회차 응답 N건을 반영했습니다` / `아직 반영할 응답이 없습니다`를 표시해 강사가 차이를 체감하게 한다.

### ADR-019: 교안은 강사 소유다. 발주 기관까지만 열람한다
**결정**: `lesson_plans`는 작성 강사의 것이다. 열람 주체는 **작성 강사 본인, 그 회차를 발주한 기관의 구성원, 운영자** 셋뿐이다. 다른 강사는 볼 수 없고, 학생·보호자에게 노출되는 경로를 만들지 않으며, anon은 0행을 받는다. 플랫폼이 교안을 익명화해 재사용하거나 다른 강사에게 참고 자료로 제공하지 않는다.

**이유**: 교안은 강사가 파는 것 그 자체다. 플랫폼이 이걸 자산화하면 강사는 도구를 쓰지 않는다. "여기서 만들면 내 노하우가 남에게 샌다"는 인식은 한 번 생기면 되돌릴 수 없고, 지금은 강사 20~30명을 모아야 하는 단계다. **초기 공급자의 신뢰가 데이터 해자보다 비싸다.**

발주 기관까지 여는 이유는 반대다. 담당 선생님은 어떤 수업이 들어오는지 사전에 확인할 의무가 있고, 교안을 미리 보는 것은 섭외 의사결정의 근거이자 기관 구독의 가치가 된다.

**트레이드오프**: 교안 코퍼스가 쌓여도 활용할 수 없다. 나중에 열려면 강사 개별 동의를 받아야 하며, 그 동의를 구독 조건으로 끼워 넣지 않는다. 뒤집을 수 있는 결정이지만 뒤집는 비용이 크다는 것을 알고 시작한다.

### ADR-020: 강사 과금은 정액 구독이 아니라 배정 연동이다
**결정**: 강사에게 월 정액 구독을 받지 않는다. **그 달에 회차를 배정받았거나 리드를 전달받은 강사에게만 과금한다.** 아무것도 받지 못한 달은 청구하지 않는다. 단가는 건당 요율로 쪼개지 않고 활동이 있는 달의 월 정액(초기 3만 원 선)으로 둔다.

**전환 트리거**: 무료 파일럿에서 유료로 넘어가는 시점을 사람의 판단이 아니라 데이터로 고정한다. **한 강사가 플랫폼을 통해 배정·리드를 누적 3건 받으면 그 다음 달부터 청구 대상**이다. 강사 화면 상단에 그 달에 받은 것(배정 N건 · 리드 N건 · 교안 N회 · 리포트 N건)을 항상 쌓아 보여준다.

**이유**: 강사가 사는 것 전부가 기관의 활동에 종속돼 있다. 파일럿 규모를 숫자로 놓으면 바로 보인다 — 기관 1~2곳에서 특강 5~10회차가 나오고 회차당 배정 강사는 1명이므로, 강사 20~30명 중 **일감이 도달하는 것은 최대 10명**이다. 나머지에게는 배정도 리드도 교안도 없다. 교안은 배정 회차가 있어야 생성되므로, 정액 구독은 **아무것도 받지 못한 강사에게 청구서를 보내는 것**이 된다. 그 청구서를 한 번 보내면 그 강사는 돌아오지 않고, 초기 공급 20~30명에서 절반을 잃으면 파일럿이 끝난다.

배정 연동은 이 문제를 가격 정책이 아니라 **정의**로 없앤다. 청구서가 나가는 달은 강사가 실제로 일감을 받은 달이므로 청구 근거를 설명할 필요가 없다. "구독을 시작시키는 것은 리드, 유지시키는 것은 교안"이라는 구조도 그대로 유지된다 — 배정을 받은 달에는 둘 다 손에 들어온다.

**트레이드오프**:
- 월 매출이 기관 활동량에 따라 출렁인다. MRR로 말할 수 없어 투자 자료에서 불리하다. 대신 이탈률이 구조적으로 낮다 — 안 쓴 달에 청구되지 않으므로 해지할 이유가 생기지 않는다.
- 배정이 몰리는 소수에게 매출이 집중된다. 소속 강사가 많은 업체는 **업체 단위로 합산 청구**한다 (ADR-010의 `providers`가 청구 주체가 된다).
- **공급(강사 수)을 늘리는 것으로는 매출이 늘지 않는다.** 매출을 늘리는 유일한 방법은 기관 회차를 늘리는 것이다. 영업 우선순위가 강사가 아니라 기관이라는 뜻이고, PRD의 사용자 우선순위(기관 1순위)와 일치한다.

### ADR-021: 회차 기획 도우미 — AI를 기관 담당자에게도 준다
**결정**: 기관·학교 담당자가 회차를 만들 때도 AI 초안을 받는다. 입력은 대상 학년·인원·시수·목적·예산대이고, 출력은 **어떤 유형의 특강이 맞는지 / 우리 지역 수요와 맞는 분야 / 강사에게 요구할 조건 / 사전 준비물** 초안이다. 구조는 ADR-017과 같은 하이브리드다 — 후보 분야와 강사 요건은 규칙(지역 공급 현황 + 미충족 수요 집계)이 확정하고 LLM은 문장만 만든다.

**이유**: 담당 선생님의 현재 대안은 꿈길도 크레존도 아니다. **작년 파일을 열어 작년 업체에 전화하는 것**이다. 비용 0, 학습 0, 리스크 0인 이 선택을 이기려면 더 좋은 강사를 보여주는 것으로는 부족하고 **지금 하는 일을 줄여야** 한다.

기관 과금의 근거도 지금까지 약했다. 강사에게는 교안과 리드가 있는데 기관에게는 리포트뿐이었고, 리포트는 "있으면 좋은" 것이지 예산을 쓰게 만드는 물건이 아니다. 회차 기획 초안은 담당자가 **지금 손으로 하는 일**을 대체하므로 결재 문서에 적을 이유가 된다.

**트레이드오프**:
- AI 화면이 둘에서 셋으로 는다. ADR-017의 "AI의 수혜자는 강사"가 "공급자와 발주자 양쪽"으로 넓어진다. **학생 쪽은 여전히 늘리지 않는다** — 그 경계는 그대로다.
- 지역 공급이 2개 분야뿐인 파일럿에서는 추천할 분야가 빈약하다. 이때는 미충족 수요를 그대로 보여주는 것이 정답이다 — "관내 VR 관심 14명, 공급 0"은 담당자에게 예산 기안의 재료가 된다.

### ADR-022: 학교 진입점은 정식 교과가 아니라 창체·진로·방과후다
**결정**: 학교 대상 가치 제안을 **창의적 체험활동·진로활동·방과후·자유학기 주제선택활동**으로 쓴다. 고교학점제 정식 선택과목 강사 공급은 MVP 범위에서 뺀다.

**이유**: 정식 교과를 맡으려면 산학겸임교사 등의 자격과 학교장 임용 절차가 필요하다(「초·중등교육법」 제22조 산학겸임교사 등). 우리 공급은 지역 직업인이고 대부분 그 자격을 갖고 있지 않다. **"고교학점제 선택과목에 강사를 공급한다"고 쓰면 교육 분야 심사자에게 바로 걸린다.** 반면 창체·진로·방과후·자유학기 주제선택은 자격 문턱이 낮고, 1호 파트너가 지금 실제로 나가는 자리도 전부 이쪽이다.

제도는 **배경**으로 정확히 쓴다 — 고교학점제(2025년 고1부터 전면 시행)로 고등학교에 과목·활동 다양화 압력이 생겼고, 그 압력이 창체·진로 쪽 외부 강사 수요로 흘러넘친다. 수요를 만드는 것은 제도이고, 우리가 들어가는 문은 자격 문턱이 낮은 쪽이다. 그리고 제도 근거는 고교학점제 하나가 아니다 — 초등은 늘봄학교, 중학교는 자유학기제 주제선택활동이 각각 더 큰 외부 강사 수요처다.

Phase 2에서 자격 보유 강사를 별도 표시하면 **자격 검증 자체가 플랫폼의 가치**가 된다. 지금은 그 문을 열지 않는다.

**트레이드오프**: 고교학점제를 전면에 내세운 문구가 약해진다. 대신 초·중을 포함하는 제도 근거가 생겨 "초·중·고 전체"라는 제품 정의가 비로소 근거를 갖는다. 순손실이 아니다.

### ADR-023: 공간 부족은 3단계로 나눈다. MVP는 기록까지만
**결정**: 후속 과정이 **장소 때문에 열리지 못하는 경우**를 사업 기회로 인정하되 단계를 나누고, MVP에서는 **1단계(기록·연결)까지만** 한다.

| 단계 | 무엇을 하는가 | 수익 | 안전·규제 부담 | 시점 |
|---|---|---|---|---|
| 1 | **장소 실패를 데이터로 기록**하고, 관내 유휴 공간(청소년수련관·평생학습관·도서관·메이커스페이스)을 강사·기관에 붙여준다 | 구독 가치 상승 | 없음 — 연결 제품 그대로 | **MVP** |
| 2 | Find My Mento 이름으로 과정을 열되 **공간과 학생 관리는 기관**이 맡는다 | 과정당 마진 | 중립성 훼손, 결제·정산 필요 | Phase 2 |
| 3 | 공간을 직접 확보하고 학생을 직접 모집·수납한다 | 가장 큼 | **학원법 등록, 학생 PII 직접 보유, 안전사고 책임** | 별도 사업 결정 |

**이유**: 문제 자체는 진짜다. 학교는 1회 특강에 그 해 예산과 시수를 이미 썼고, 지역 강사는 자기 공간이 없다. **수요가 확인되고 강사도 있는데 열 곳이 없어서 무산되는 경우**가 실제로 생긴다. 단가로 보면 이 모델이 지금까지 검토한 것 중 가장 크다 — 단기과정 하나(정원 8~12명 × 4~8회)가 강사 과금 수십 건에 해당한다.

그러나 3단계는 **제품의 정체성을 바꾼다.**

- **중립성이 무너진다.** 플랫폼이 공급자가 되면 추천이 자사 과정을 밀지 않는다는 것을 증명할 수 없다. 기관이 수요 데이터를 믿지 않게 되는 순간 기관 과금과 지자체 제안이 통째로 사라진다 (ADR-009).
- **학생 PII를 직접 갖게 된다.** 지금 설계의 전제는 "플랫폼은 연결만 하고 학생 관리 책임은 기관에 있다"이다. 직접 모집하면 이름·연락처·보호자 동의·출결·안전사고 책임이 전부 플랫폼으로 온다. ADR-003이 무너진다.
- **학원법 등록 대상이 될 수 있다.** 유료로 지속적인 교습을 하면 「학원의 설립·운영 및 과외교습에 관한 법률」상 학원·교습소 등록 의무가 생길 수 있다. 요건은 반드시 법령 원문과 관할 교육지원청으로 확인해야 한다.
- **확장성이 사라진다.** 수도권 66개 시군구로 넓히는 것은 소프트웨어의 일이지만, 과정을 직접 운영하는 것은 지역 한 곳에 사람이 묶이는 일이다.

그래서 3단계는 "하지 않는다"가 아니라 **"플랫폼 사업과 별개의 결정으로 다룬다"**로 둔다. 마진이 크다는 이유로 지금 섞으면 플랫폼 쪽 수익모델 두 개(기관 과금·지자체 제안)를 잃는다. **2단계는 중립성 훼손이 1단계와 3단계의 중간이므로, 넘어갈 때 ADR-009를 다시 열어 "자체 개설 과정은 추천 순위에서 제외한다"를 명문화해야 한다.**

**MVP에서 지금 하는 것**: `recruitment_requests`의 종료 사유에 **`장소 없음`**을 별도 값으로 둔다. 미충족 수요 집계에서 "공급 없음"과 "장소 없음"을 구분해 센다. 이 숫자가 쌓이기 전에는 2·3단계를 판단할 근거가 없고, 쌓이면 그 자체가 제안 자료가 된다 — *"관내에서 수요와 강사가 다 있는데 장소가 없어 무산된 과정 7건."*

**트레이드오프**: 단가가 가장 큰 모델을 뒤로 미룬다. 그러나 1단계 데이터 없이 3단계로 가면 **얼마나 필요한지도 모르는 공간에 고정비를 쓰는 일**이 된다. 순서가 뒤집히면 안 되는 종류의 결정이다.

### ADR-024: 수업 후 AI 3종 — 결과보고서·후속 과정 제안·수업 회고. 저장하지 않고, 숫자는 규칙이 확정한다
**결정**: 수업이 끝난 뒤의 업무에 AI 초안 기능 3개를 넣는다.

| # | 기능 | 사용자 | API | 화면 버튼 |
|---|---|---|---|---|
| 4 | 결과보고서 초안 | 발주 기관·학교 구성원 | `POST /api/result-report` | `결과보고서 초안 만들기` |
| 5 | 후속 과정 제안 + 섭외 요청 문안 | 발주 기관·학교 구성원 | `POST /api/followup-plan` | `후속 과정 제안받기` |
| 6 | 수업 회고 + 학교 제출용 결과 요약 | 배정 강사 | `POST /api/session-debrief` | `수업 회고 만들기` |

세 기능은 아래 규칙을 공유한다.

1. **아무것도 저장하지 않는다.** 초안을 생성해 화면에 보여주고 복사할 수 있게 할 뿐이다. 새 테이블·새 RLS 정책이 없다.
2. **숫자·후보·사실은 규칙이 확정하고 LLM은 문장만 쓴다** (ADR-004·017·021과 같은 하이브리드). LLM이 실패하면 규칙 초안으로 200을 반환한다.
3. **응답 5건 미만 회차는 만족도·후속 의향·관심 분야·학생 의견을 싣지 않고 LLM도 부르지 않는다.** ADR-018의 k-익명성 임계치를 수업 후 AI에도 그대로 적용한다.
4. **숫자 가드**: LLM 문장에 규칙이 주지 않은 숫자가 있으면 그 문장을 버린다 (환각 수치 차단).
5. **이름 가드**: LLM 문장에 강사명·기관명·업체명이 들어가면 버린다. 연락처·링크는 `maskForStorage`로 거른다.
6. **학생 개인을 지목·평가하는 문장을 만들지 않는다.** 단위는 회차다.
7. **결과보고서의 창체 진로활동 기록 참고 문구는 회차 단위 활동 서술 한 문장이다.** 2026 학교생활기록부 기재요령에 따라 강사명·기관명·상호명을 넣지 않고, "AI 문장을 그대로 입력하지 말 것 / 학교가 주최·주관한 활동에만 기재 가능"을 화면에 고지한다. 학생 개인별 특기사항 문장은 만들지 않는다 (영구).
8. **후속 과정 제안은 모집·정원·수강료·신청 폼을 다루지 않는다** (ADR-023). 강사 후보는 규칙이 고르며 정렬은 거리·이름뿐이고 소속 업체·구독·결제 여부를 반영하지 않는다 (ADR-009). 섭외 요청을 자동 발송하지 않는다 — 기관이 기존 섭외 화면에서 직접 보낸다.
9. **권한**: 기능 4·5는 `org_member`이면서 **자기 기관의 회차**일 때만, 기능 6은 `instructor`이면서 **그 회차의 배정 강사**일 때만. 역할은 `org_members`/`instructors` 소속으로만 판별한다. 역할이 틀리면 403, 회차가 없거나 남의 회차면 404 — 존재 여부를 구분해 흘리지 않는다.

**이유**: 지금까지 AI는 수업 **전**(ADR-017 교안·ADR-021 회차 기획)과 **직후**(ADR-004 추천)에만 있었다. 그런데 **돈을 내는 쪽의 반복 노동은 수업이 끝난 뒤에 온다.** 기관 담당자는 만족도를 집계해 결과보고서를 쓰고, 후속 과정을 열지 판단하고, 강사에게 보낼 섭외 문안을 쓴다. 강사는 수업을 돌아보고 학교에 낼 결과 요약을 따로 만든다. 여기에 AI가 없으면 철학 5번("AI는 공급자의 도구다")이 수업 후에서 끊긴다.

조사(`docs/AI_RESEARCH.md`)가 같은 자리를 가리킨다. AI로 줄일 수 있는 반복 문서 작업 Top 5 중 5번이 **"만족도 집계 → 결과보고서 초안 + 회차 단위 활동 요약"**이다 — 방과후는 만족도 조사가 의무이고, 교외 체험은 실시 후 만족도 조사·자체 평가회를 하고, 청소년수련활동 인증제는 활동 종료 후 결과보고 등재를 요구한다. 시장에서는 생기부 초안·평가 문항·학생 개인 맞춤 같은 교과 교사용 AI가 포화인 반면, **외부강사 특강의 회차 후 요약·결과보고·후속 프로그램 제안**은 공백이다. 규제도 학생 식별정보·학생 평가·학생부 기록에 몰려 있어, 회차 단위로만 다루는 이 설계는 규제 방향과 맞는다.

결과보고서는 ADR-021이 짚은 약점을 메운다. 기관에게 리포트는 "있으면 좋은" 화면이었지 예산을 쓰게 만드는 물건이 아니었다. 결과보고서 초안은 담당자가 **지금 손으로 쓰는 문서**를 대체하므로 결재 문서에 적을 이유가 된다.

후속 과정 제안은 **주 지표(기관의 섭외 요청 발송)로 곧장 이어진다.** 수요 숫자·강사 후보·문안이 한 화면에 있으면 섭외 화면까지 한 단계다. 그래도 발송은 사람이 한다 — 섭외 요청은 기관 이름으로 강사에게 나가는 요청이고, 보낼지 말지가 곧 기관의 판단이다.

숫자를 규칙이 확정하는 이유는 이 문서들이 **제출된다**는 데 있다. 교안의 어색한 문장은 강사가 수업 전에 걸러내지만, 보고서의 틀린 숫자는 결재선을 타고 올라간다. 저장하지 않는 이유는 비용이다 — 저장하면 교안처럼 소유·열람 범위(ADR-019)를 다시 정하고 RLS 정책과 네거티브 테스트를 더해야 한다. 초안은 같은 집계에서 언제든 다시 만들 수 있으므로 저장할 이유보다 저장 비용이 크다.

**트레이드오프**:
- **저장하지 않으므로 생성 이력으로 품질을 추적할 수 없다.** 검수는 `source`(`llm`/`rule`) 로그로만 한다. 담당자가 고쳐 쓴 최종본이 무엇이었는지도 모른다.
- **숫자 가드가 정상 문장도 버릴 수 있다.** 규칙이 준 비율이 49%인데 LLM이 "약 50%"로 옮겨 쓰면 그 문장은 버려진다. 그때는 규칙 문장이 나온다. 덜 매끄러운 문장이 틀린 숫자가 실린 보고서보다 싸다.
- **창체 참고 문구는 규제가 강화되면 제거할 수 있게 한 필드로만 둔다.** 교육청 단위로 정성 기록에 AI 사용을 금지하는 지침이 이미 나왔다(전북교육청 2026-08). 결과보고서의 나머지 구조는 이 필드에 의존하지 않는다.
- 응답 5건 미만 회차에서는 세 기능이 거의 빈 초안을 낸다. 소그룹 회차에서 자주 일어날 것이다. ADR-018과 같은 이유로 의도한 손실이다.
- AI 화면이 셋에서 여섯으로 는다. **학생 쪽은 여전히 늘리지 않는다** — 여섯 중 학생에게 가는 것은 추천 카드 하나다.

### ADR-025: 데모 배포에는 시연용 AI 응답을 켠다. 실 DB 배포에서는 절대 켜지지 않는다
**결정**: LLM 키가 없는 **데모 데이터 모드** 배포에서는 AI 기능 6개가 규칙 문장 대신 **시연용 AI 응답**을 쓴다 (`src/lib/ai/demo-writer.ts`).

1. **켜지는 조건은 셋이 모두 맞을 때뿐이다**: 데모 데이터 모드(Supabase 키 없음) · `ANTHROPIC_API_KEY` 없음 · `DEMO_AI`가 `off`가 아님. 키가 들어오면 실제 LLM이 우선이고, 실 DB에 붙으면 키가 없어도 규칙 결과다.
2. **시연 응답은 LLM과 같은 입구·출구를 쓴다.** 각 기능이 LLM에 보내는 페이로드만 읽고 LLM이 돌려줄 JSON과 같은 모양을 만든다. 그 결과는 실제 LLM 응답과 **같은 병합·가드**(문장 정리 → 숫자 가드 → 이름 가드 → 모집 단어 가드)를 통과해야 화면에 남는다. 숫자·후보·항목·고지문은 규칙 값 그대로다.
3. **페이로드에 없는 사실을 만들지 않는다.** 학생 의견 요약은 주어진 인용에 실제로 있는 주제만 쓴다. 표본 5건 미만 회차는 시연 모드에서도 LLM 경로를 타지 않는다.
4. **화면에서 숨기지 않는다.** 시연 응답이 쓰인 초안은 source 표시가 `시연용 AI 문장입니다`로 바뀌고, 대시보드 상단 데모 안내에 "AI 문장은 시연용 예시"를 적는다. `/api/health`의 `ai_mode`가 `llm` / `demo` / `rule` 중 하나를 돌려준다.
5. 테스트는 기본값이 `DEMO_AI=off`다 (`vitest.setup.ts`). 시연 경로는 `tests/demo-ai.test.ts`에서만 켠다.

**이유**: 데모 배포는 창업 지원 심사와 파일럿 기관 설명 자리에서 쓰인다. 거기서 보여줘야 하는 것은 "규칙 템플릿이 돈다"가 아니라 **"LLM을 붙이면 담당자·강사의 문서 작업이 이만큼 줄어든다"**다. 그런데 키를 데모에 넣으면 공개 URL로 누구나 호출할 수 있어 비용 상한을 둘 수 없다.

시연 응답을 **가드 뒤에** 둔 이유는 시연이 설계를 증명해야 하기 때문이다. 시연 문장이 숫자 가드를 우회하는 별도 경로였다면 데모 화면은 "실제로는 가드에 걸려 버려질 문장"을 보여줄 수 있다. 같은 파이프라인을 통과시키면 시연 화면이 곧 키를 넣었을 때의 상한선이다 — 시연 문장이 가드에 걸리면 테스트가 먼저 깨진다.

**트레이드오프**:
- **시연 문장은 입력에 반응하는 템플릿이다.** 실제 LLM만큼 회차마다 다르지 않다. 데모 데이터 5회차에 맞춰 다듬었으므로 새 분야·새 조건에서는 어색할 수 있다.
- 시연 모드를 실제 AI로 오해할 수 있다. 그래서 source 문구와 상단 안내에 "시연용"을 적는다. **심사·기관 앞에서는 "LLM 연결 전 시연 응답"이라고 소개한다** — 물어보면 드러나는 것을 먼저 말한다.
- 실 DB 배포에서 키가 빠지면 시연 문장이 아니라 규칙 문장이 나온다. 실제 기관 화면에 미리 쓴 문장이 나가는 것이 규칙 문장이 나가는 것보다 훨씬 나쁘다.

### ADR-026: 학생·보호자도 데모에서 들어가 본다. 보호자에게는 문의 도우미를 준다 — 계정·저장 없이
**결정**:

1. **데모 입구**: `/login` 데모 블록에 "계정 없이 쓰는 사람" 두 줄을 더한다. 학생은 `/s/735104`(QR 설문 → 추천), 보호자는 `/inquiry`(문의 도우미 → 문의)로 곧장 연다. **역할 버튼이 아니다** — 쿠키를 심지 않고 `Actor`에 역할을 더하지 않는다. `enterDemo`는 `student`·`guardian` 키를 거부한다. 학생·공개 화면 상단에는 데모 안내와 "역할 다시 고르기" 링크를 둔다 (실 DB에서는 렌더되지 않는다).
2. **학생 AI는 늘리지 않는다.** 데모 학생 입구에 지난 회차 기록이 있는 가명코드(`311009`)를 적어, 기존 추천(기능 1)의 누적 이력 반영(E-18)이 보이게만 한다.
3. **보호자 문의 도우미 (AI 기능 7)**: `/inquiry` 폼 안에서 보호자가 아이 상황을 적으면 `POST /api/inquiry-assist`가 (a) 학년대·관심 분야·희망 시간대를 **규칙**으로 정리하고 (b) 공개 디렉토리와 같은 함수(`searchDirectory`)로 조건에 맞는 프로그램을 최대 3개 고르고 (c) LLM이 강사가 답할 수 있는 **문의 글 한 편**(300자 이내)을 쓴다. 보호자가 `이 내용으로 폼 채우기`를 눌러야 폼에 들어가고, 접수는 기존 `/api/inquiry` 하나뿐이다.
4. **아이 식별 정보는 LLM에 가기 전에 지운다.** `lib/moderation` 마스킹 → 줄여 쓴 학교명("광명중 2학년") → 나이·생년 → 학년 숫자 순. LLM 글에 숫자·가림 표시·학교명·연락처·링크가 있으면 버리고 규칙 글을 쓴다. LLM 응답에서 읽는 값은 `message` 하나뿐이다.
5. **저장하지 않고, 역할을 보지 않는다.** 비로그인 라우트지만 어떤 테이블에도 쓰지 않고 `inquiries`·학생 기록을 읽지 않는다. 레이트 리밋은 IP당 1분 10회. 시연 응답(ADR-025)은 이 기능에도 같은 입구·가드로 적용된다.

**이유**: 데모를 보는 사람(심사위원·기관)은 "학생과 보호자는 어디서 뭘 보나"를 묻는다. 계정이 없다는 것이 답인데, 화면에 입구가 없으면 기능이 없는 것처럼 보인다. 입구를 **역할 버튼**으로 만들면 데모가 실제 설계와 달라진다 — 학생·보호자 로그인이 있는 것처럼 보이고, 쿠키로 역할을 얻는 경로가 하나 는다. 그래서 실서비스와 같은 비로그인 경로를 그대로 연다.

보호자 도우미는 AI.md 원칙("AI는 공급자의 실행 도구")을 깨지 않는 선에서만 연다. 보호자 문의는 강사에게 전달되는 **리드**이고(ADR-014), 리드 품질이 강사 구독의 두 번째 가치다. 지금 보호자 문의는 "연락 주세요" 한 줄이거나, 반대로 아이 실명·학교를 적어 온다(E-22). 도우미는 두 문제를 같은 자리에서 푼다 — 강사가 답할 조건을 채우고, 아이 정보는 LLM에 가기 전에 빠진다. **학생 데이터는 늘지 않고, 학생 개인의 수준 진단·학습경로도 만들지 않는다** — 공개 디렉토리의 필터 세 개를 보호자 대신 채우는 일까지다.

**트레이드오프**:
- **조건 정리는 키워드 규칙이다.** "마인크래프트로 집 짓기"처럼 분야 단어가 없는 글에서는 분야를 못 찾는다. 그때는 비워 두고 보호자가 칩으로 고른다. LLM에게 분야를 고르게 하면 더 잘 찾겠지만, 사실은 규칙이 확정한다는 원칙(ADR-021·024)을 이 기능에서만 깨지 않는다.
- **줄인 학교명 규칙에는 오탐이 있다**("가지고 다니"). LLM에 가는 설명이 조금 거칠어질 뿐 저장되는 값은 없다. 공용 `lib/moderation`은 바꾸지 않았다 — 설문·Q&A·문의 저장 규칙이 같이 바뀌기 때문이다. 따라서 보호자가 도우미를 쓰지 않고 요청 내용 칸에 "광명중 2학년"을 직접 적으면 저장 시 가려지지 않는 틈은 그대로다.
- 비로그인 LLM 경로가 하나 는다. 비용 상한이 IP 레이트 리밋뿐이다. 파일럿 규모에서는 무시할 만하지만, 실 LLM 키를 넣고 공개 홍보를 시작하기 전에 서버 측 일일 상한을 붙여야 한다.
- 도우미의 "조건에 맞는 프로그램"은 학생도 볼 수 있다. 공개 디렉토리와 같은 정보이고 강사에게 닿는 버튼이 없으므로 새 연결 경로는 아니다. 접수에는 여전히 보호자 이름·연락처·동의가 필요하다.

### ADR-027: 추천할 수업이 0건이면 진로 카드 3장을 보여 준다 — 후보는 검수 목록, LLM은 고르고 이유만
**결정**: 학생 결과 화면에서 수업 추천이 0건(E-07)이면 빈 안내 대신 **진로 방향 카드 3장**을 보여 준다 (`src/lib/ai/career.ts`, 목록 `src/data/careers.ts`).

1. **후보는 검수된 목록뿐이다.** 직업 18개(설문 분야마다 2개 이상)에 하는 일 한 문장과 관련 학과·자격을 사람이 적어 둔다. 규칙이 학생이 고른 분야·오늘 분야·자유서술 키워드로 후보를 최대 8개 확정하고, LLM은 그중 3개를 고르고 이유 한 줄만 쓴다. 목록 밖의 직업·자격증·학교는 나갈 수 없다.
2. **학생 수준 평가·학습 순서는 만들지 않는다.** 프롬프트로 막고, 이유 문장에 수준 평가 표현·숫자(3D 제외)·연락처·링크가 섞이면 그 카드만 규칙 문장으로 바꾼다. 카드에는 직업 이름·하는 일·관련 학과/자격·이유 한 줄만 들어간다.
3. **LLM에는 가린 값만 간다.** 학년대·오늘 분야·후속 의향·고른 분야·가린 자유서술(Q5·Q6)까지다. 이름·학교·가명코드는 페이로드에 없다.
4. **실패는 규칙으로 떨어진다.** 키 없음·한도·크레딧 소진·타임아웃·거절·JSON 파싱 실패 → 규칙 선택 + 규칙 문장. Opus 5 요청에는 서버 측 거절 대체(`fallbacks: "default"`)를 켠다.
5. 학생이 누르는 버튼은 늘지 않는다. 진로 카드에는 강사·기관으로 가는 버튼이 없다.

**이유**: 첫 실제 파일럿(부천 소사 청소년센터 드론코딩, 2026-09-19)에는 등록된 후속 과정이 없다. 기존 설계대로면 학생은 설문을 마치고 "지금은 바로 들을 수업이 없어요"를 본다 — 파일럿에서 과반으로 예상한 경로(E-07)가 가장 비어 있는 화면이다. 창업자가 이 자리에 AI로 진로 방향을 보여 주기로 결정했다(2026-09-18). 그래서 ADR-026의 "학생 AI는 늘리지 않는다"와 AI.md의 "기능 1은 더 키우지 않는다"를 **이 경로에 한해** 푼다. 대신 기능 1과 같은 구조(규칙 후보 + LLM 선택)를 그대로 써서, CLAUDE.md가 막는 것(수준 진단·개인 학습경로·장기 프로필)은 여전히 만들지 않는다.

**트레이드오프**:
- 목록이 짧다. 목록에 없는 꿈(예: 요리사)을 적은 학생에게는 오늘 분야와 가까운 진로만 나온다. 목록은 사람이 검수해서 늘린다.
  - **보완 (2026-09-19, 파일럿 첫 피드백 "요리사가 꿈인데 드론 조종사가 나온다")**: 요리와 이어지는 기술 직업 둘(푸드테크 개발자·조리 로봇 엔지니어)을 목록에 더했다. 꿈과 이어지는 카드는 LLM 순서와 상관없이 **맨 앞**에 둔다. 목록에 없는 꿈이면 카드 위에 **응원 한 줄**을 보여 준다 — LLM 이 "오늘 분야가 그 꿈과 만나는 장면"을 쓰고(가드 통과), 실패하면 학생의 말을 되풀이하지 않는 규칙 문장이다. 꿈이 목록과 이어지는지는 규칙(키워드)이 정하고 LLM 이 정하지 않는다. 새 직업·자격을 만드는 경로는 여전히 없다.
  - **꿈 잇기 직업 (같은 날, 피드백 "변호사라고 썼는데 드론 조종")**: 아이들이 많이 적는 꿈과 오늘 기술을 잇는 실제 직업 여섯(기술 전문 변호사·스포츠 데이터 분석가·의료 인공지능 개발자·드론 라이트쇼 연출가·3D 애니메이터·생태 조사 연구원)을 더했다. 요리 둘과 함께 `dreamOnly` — 그 꿈이나 관련 말을 쓴 학생에게만 후보가 되고, 분야만 겹친다고 나가지 않는다. 일반 문장에 흔한 말('배우' ← "배우고 싶어요")은 `jobKeywords` 로 관심 직업 칸에서만 맞춘다.
- **운영자 화면 (같은 날, 사용자 요청)**: `/admin/sessions` 에서 모든 회차의 응답·AI 추천 현황을, `/admin/sessions/{id}` 에서 응답 하나하나와 그 학생이 본 카드·이유·AI 여부·비용을 본다. 추천 기록은 RLS 로 운영자·자기 기관만 읽는다.
- 추천할 수업이 0건일 때 학생 한 명당 LLM 호출이 한 번 생긴다(수업 추천은 후보가 없으면 원래 호출하지 않는다). 호출당 수 센트다.
- 카드가 맞았는지는 학생 반응으로만 알 수 있다. 무엇을 보여 줬는지는 추천 기록으로 남긴다.
